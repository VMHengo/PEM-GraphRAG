# Directed Multi-Hop Staging Runbook

Use this runbook after changing directed extraction, routing, Neo4j traversal,
or context formatting. It defines the technical completion criteria for the
directed-retrieval MVP. It does not replace a domain expert's review of the
expected chains.

## 1. Freeze And Back Up

1. Confirm the Git checkout is clean and note the revision:

   ```bash
   git status --short
   git rev-parse --short HEAD
   ```

2. Take a provider snapshot or a stopped-volume backup of the staging Neo4j
   data and the staging `rag_storage` directory. Keep the backup outside the
   checkout and exclude `.env` files from Git.
3. Record the current benchmark result before changing prompts, embeddings, or
   retrieval logic. A benchmark is only comparable when its document corpus,
   embedding model, and benchmark JSON are unchanged.

## 2. Build Staging

Run the commands on the staging host. Substitute the tracked or locally
maintained staging compose path where shown:

```bash
cd ~/PEM-GraphRAG
docker compose \
  --project-name pem-staging \
  --env-file .env.staging \
  -f deploy/mcp/docker-compose.staging.yml \
  up -d --build lightrag mcp-gateway oauth2-proxy
```

Wait for LightRAG and the MCP gateway to be healthy. Do not point production
ChatGPT connectors at this endpoint.

## 3. Controlled Evidence Corpus

Ingest a small text or PDF corpus containing all three verified patterns:

```text
Process parameter -> intermediate property -> defect
Defect -> upstream root cause
Production step -> downstream process or artifact
```

Re-extract these documents after every prompt or extraction-model change. Old
edges remain queryable as `unknown`, but they cannot be treated as proof that
the new directed extraction behaved correctly.

In Neo4j, inspect newly extracted relationships:

```cypher
MATCH (a)-[r]->(b)
WHERE r.relation_type IS NOT NULL
RETURN a.entity_id AS source,
       r.relation_type AS relation_type,
       r.directionality AS directionality,
       r.relation_importance AS importance,
       r.chain_role AS chain_role,
       b.entity_id AS target
LIMIT 50;
```

## 4. Query Acceptance Checks

Use the Retrieval WebUI with retrieval diagnostics enabled, or the dedicated
MCP tool `trace_pem_graphrag_chain`.

1. Root-cause question: choose `auto` and verify it resolves to `combined`
   with `edge_direction=in`.
2. Consequence or production-chain question: verify `edge_direction=out`.
3. General knowledge question: verify `auto` resolves to `normal` and reports
   `strategy_normal` without calling the directed neighbor provider.
4. For every directed path used in context, verify `citable_path_count > 0`
   and inspect the corresponding references. Uncited paths may appear in
   diagnostics but must not appear in the answer context.

## 5. Benchmark Gate

Open the WebUI **Evaluation** tab and run
`pem_directed_retrieval_quality` in `retrieval` mode. The benchmark compares
`normal`, `directed`, `combined`, and `auto` using context-only calls, so it
does not generate an answer for each strategy.

Promotion requires all of the following:

- configured Quality Gates pass;
- no expected directed path is missing;
- required citations resolve to stored source chunks;
- the normal strategy still reports zero directed paths;
- a PEM domain reviewer accepts the expected causal and production chains.

Save the result JSON under `rag_storage/evaluation_runs` together with the
commit hash and document-set version. This is the release evidence.

## 6. Production Promotion And Rollback

Promote only the reviewed Git commit and the matching benchmark JSON. Take a
fresh production backup before rebuilding. Keep
`MCP_RETRIEVAL_STRATEGY=normal` as the general connector default; the
dedicated chain-tracing tool remains available for bounded diagnostics.

If a regression appears, redeploy the previous image/commit and restore the
matching data backup. Do not mix a restored Neo4j database with vector storage
generated by a different embedding model or prompt profile.
